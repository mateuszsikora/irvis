# Desktop app

## Data flow

`apps/desktop/src/main.js` registers `app://irvis/` before readiness and serves only `apps/web/dist` through `protocol.handle` and `net.fetch(file:)`. The scheme enables standard URLs, secure context, fetch, streaming; CORS is disabled by default. Paths are decoded and restricted to the build directory; other hosts and non-GET/HEAD requests are denied.

The sandboxed window has context isolation enabled and Node integration disabled. Its CSP allows app scripts, Workers, fetch and media, without disabling CSP. Navigation and new windows are denied. Media permission is granted only to the app window and app origin.

`preload.cjs` exposes device enumeration, a device's video modes, profile commands, recording storage, start, stop and subscription callbacks, never IPC events or arbitrary channel access. The main process validates sender, main frame, profile, mode and platform-specific device selector. `capture:start` resolves the mode id with `findVideoMode()` from `@irvis/core`: a mode of the profile, with or without temperature data, or an image-only mode `image-<width>x<height>@<fps>` that the renderer took from the device's modes ([core technical](core-technical.md#image-only-video-modes)); any other id throws `Invalid capture selection`. Camera control is opened only for a mode the profile lists, because another mode may belong to another camera than the profile's USB IDs find. `capture.js` builds ffmpeg arguments from the mode; capture-cli supplies executable discovery. `listDevices()` in `capture.js` answers `capture:devices`: on macOS the AVFoundation video devices from `ffmpeg -list_devices` except screens (`Capture screen <n>`) (id: the index; label: the name), on Windows the DirectShow video devices (id and label: the name), and on Linux the `/dev/videoN` nodes in number order (id: the path; label: `/sys/class/video4linux/videoN/name`, or `videoN` when that file cannot be read). Each device also gets `vendorId` and `productId` where the system tells them: on macOS from `/usr/sbin/system_profiler SPCameraDataType -json`, run next to ffmpeg and stopped after 3 s, whose `spcamera_model-id` is `UVC Camera VendorID_<decimal> ProductID_<decimal>` for a USB camera, matched by name (`parseCameraData`; a name listed with two different pairs gets none, and a failed run lists the devices without IDs); on Windows from the `vid_<hex>&pid_<hex>` in the `Alternative name` line that follows the device (`parseDshowDevices`, which strips the log context that Windows prints without `0x`); on Linux from `/sys/class/video4linux/videoN/device/../idVendor` and `idProduct`. `listModes(platform, device)` answers `capture:modes` with the device's modes `{ width, height, minFps?, maxFps? }`, read by `parseDeviceModes` from the output of `modesArgs`: on macOS `modesProbeArgs` from `tools/capture-cli/src/ffmpeg.ts` (`-video_size 1x1`, which AVFoundation rejects with its `Supported modes`, any pixel format, through `parseSupportedModes`), each mode at the maximum of its range as both `minFps` and `maxFps`, because ffmpeg's AVFoundation input opens a format only when `-framerate` is within 0.01 of its maximum frame rate (`libavdevice/avfoundation.m`), unrounded (`30.00003`); on Linux first `v4l2-ctl --list-formats-ext -d /dev/videoN` (v4l-utils), whose `'YUYV'` sizes `parseV4l2CtlModes` reads as one mode for each discrete rate of their `Interval` lines and one with the range of a stepwise or continuous rate (a size whose rates are missing or not all readable is one mode without a rate; both `[0]: 'YUYV'` and the older `Pixel Format: 'YUYV'` format lines are read; [decision](../decisions/architecture.md#on-linux-a-modes-frame-rate-comes-from-v4l2-ctl-or-from-the-driver)), and only when `v4l2-ctl` is missing, fails or lists no YUYV size, `-f v4l2 -list_formats all`, the sizes of the `Raw : yuyv422` line, without frame rates; on Windows `-f dshow -list_options true`, the `pixel_format=yuyv422` lines with one size. Sizes given as a range are left out, repeated modes are dropped, and the device selector is validated as for capture (`Invalid capture selection`). A run is stopped after 10 s with `Reading the camera modes timed out`; `v4l2-ctl` is stopped after 3 s and then falls back to ffmpeg. `main.js` reads through `modesReader(list)` from `capture.js`, one read at a time, passing each run an `AbortSignal`. A new `capture:modes` request kills the read before it, whose request answers with an empty list, so fast Source changes do not leave ffmpeg processes running. Every `capture:start` calls `pause()`, which kills the read in progress and holds new ones until every pause is released, each by the function `pause()` returned, so that capture does not open the device next to a read; then a read that the start stopped reads the modes again, so its request still answers with the camera's modes. `captureReadPause(platform, release)` decides when a started capture releases its pause: on macOS and Linux when ffmpeg's stderr first gives the input's pixel format, so it has opened the device, and on every platform when the process emits `error` or `close`, which on Windows is the only release, because DirectShow may not let a second process open a capturing device. A start that throws or gives up before spawning ffmpeg releases its pause at once. A capture that ends while a newer one starts releases only its own pause. The wiring in `main.js` (which events call `opened` and `ended`) has no unit test. On macOS reading the modes of the T7 while it captures in another process works; on Linux and Windows neither the device IDs nor the modes have been run against real devices, and on Windows it is not known whether a mode read and a capture of the same device can overlap. A Linux node whose `/sys/class/video4linux/videoN/index` is not `0` is a second node of the same device, such as a UVC camera's metadata node, and is left out. `test/capture.test.js` covers the Linux list with a stubbed file system, the macOS and Windows lists with stubbed program output, the mode arguments and parsing for each platform (an AVFoundation mode at its maximum rate), `v4l2-ctl` output with discrete and continuous rates, a stepwise size and the older format lines, `listModes` on Linux with `v4l2-ctl`, without it, with it failing and when stopped, `modesReader` reading again after a stopped read, answering an empty list to a replaced one and holding reads until every pause is released, `captureReadPause` on each platform, the signal passed through `listModes`, and camera data that is not JSON or has no camera list; the Linux list has not been run against real Linux devices. No renderer argument becomes an executable path or arbitrary ffmpeg option.

Capture packs native bytes without pixel conversion. stderr must confirm native `yuyv422`; any other detected format stops capture with `pixelFormatMessage(format, mode)` from `src/capture.js`: `Exact reference requires native yuyv422; received <format>` for a mode with temperature data, `This camera sends <format>, not YUYV, in this video mode; choose another video mode.` for an image-only one. Format detection parses only newline-terminated log lines, retaining an incomplete suffix for the next stderr chunk, so a split format token is never treated as a different format. `frameReader(size, onFrame)` in `src/capture.js` cuts stdout into fixed `width * height * 2` frames: it copies each chunk once into one reused frame buffer, so an image-only frame of several megabytes is not rebuilt with every pipe chunk, and `main.js` copies a frame only when it sends it. Only one reference IPC message may be outstanding; preload acknowledges after callback processing, so surplus frames are dropped. When ffmpeg exits, `captureEndedMessage(code, log, mode)` in `src/capture.js` turns its stderr into the viewer's error, after removing each line's context prefix such as `[in#0 @ 0x7c5101c000] ` with `stripLogPrefix` from `tools/capture-cli/src/ffmpeg.ts`. If the log contains AVFoundation's `Selected video size (<w>x<h>) is not supported by the device`, the message is `This camera has no <width> × <height> video mode; it offers <sizes>. It is probably not the thermal camera: choose another camera in Source.` for a mode of the profile (`captureEndedMessage(code, log, mode, profileMode)` gets from the main process the same `profile.videoModes.includes(mode)` that decides camera control), with temperature data or not, which App also offers when the camera's modes could not be read, and `This camera has no <width> × <height> video mode; it offers <sizes>. Choose another video mode.` for an image-only mode `image-<w>x<h>@<fps>`, which came from that camera's own list, with each size that `parseSupportedModes` (also from `tools/capture-cli/src/ffmpeg.ts`) reads from `Supported modes` listed once, in log order (without sizes it ends after `video mode`). Otherwise it is `Capture ended (<code>).` followed by ffmpeg's last four non-empty lines, one per line; `.error-notice` in `apps/web/src/viewer.css` keeps those line breaks. V4L2 and DirectShow word a missing mode differently and get the second form. `test/capture.test.js` covers both forms, both pixel-format messages and frames cut across chunk boundaries from one buffer. Stop, main-frame navigation to a new document (including reload), renderer failure, window close and app quit terminate ffmpeg; a two-second timeout escalates to SIGKILL. When macOS lacks camera access, AVFoundation still lists the camera and ffmpeg opens it, but waits for its first frame for ever, without an error. So before spawning ffmpeg, `startCapture` reads `cameraAccess(platform, systemPreferences)` from `src/capture.js`: Electron's `systemPreferences.getMediaAccessStatus('camera')` on macOS. On Linux and Windows the app does not read the system's camera setting and takes `granted`. On `denied` or `restricted` it does not start ffmpeg and sends `cameraAccessMessage(access, app.isPackaged)` on `capture:error`. It sends rather than throws, because the viewer would show a thrown message after Electron's `Error invoking remote method 'capture:start': Error:` prefix. `denied` in a package gives `macOS does not let irvis use the camera. Allow irvis in System Settings → Privacy & Security → Camera, then press Start again.` From the repository, where macOS attributes the camera to the app that started Electron, it gives `macOS does not let irvis use the camera. Allow the app that started irvis, such as Terminal, in System Settings → Privacy & Security → Camera, then press Start again. An app missing from that list cannot be given camera access; start irvis from Terminal instead.` `restricted` cannot be changed in System Settings and gives `macOS does not let apps use the camera on this Mac: a device management profile or Screen Time restricts it. Ask the Mac's administrator.` On `not-determined` ffmpeg starts, and macOS asks when it opens the camera; the app does not call `askForMediaAccess`, which could wait for an answer on a CI runner.

A capture with no frame `firstFrameTimeout` (10 s) after spawning stops with `noFramesMessage(platform, access, packaged)`, with the permission read again at that moment. Each message starts with `The camera sent no image within 10 s.` What follows depends on the system and the permission:

- macOS, `denied` or `restricted`: the message above.
- macOS, a package with `granted`, and Linux: `Choose another camera in Source or reconnect this one, then press Start again.`
- macOS, `not-determined`, or `granted` from the repository: `macOS sends no image to an app without camera access. If macOS asks for camera access, allow it and press Start again; otherwise allow irvis in System Settings → Privacy & Security → Camera, then press Start again.`, with the repository's advice to allow the app that started irvis. The advice stays with `granted` from the repository because it has not been checked whether Electron's status there is that of the app macOS attributes the camera to.
- Windows: the Linux text, followed by `If Windows blocks the camera, turn on Let desktop apps access your camera in Settings → Privacy & security → Camera.`. How DirectShow behaves with camera access turned off has not been checked.

Started from an agent app that has no camera usage description, such as Conductor, the status is `not-determined`, macOS shows no prompt, and only the 10 s message appears. `test/capture.test.js` covers the status read and every message; the timer in `main.js` has no automated test.

## Schema

The reference has `kind: yuyv`, profile dimensions, Uint8Array bytes, main-process monotonic `timestamp` and wall-clock `receivedAt`, plus the latest optional `cameraState` snapshot. Timestamps represent receipt, not camera exposure. The bridge start request contains only `profileId`, `modeId` and `device` (AVFoundation index, `/dev/videoN` path or DirectShow video name).

## Configuration

`src/ffmpeg.js` `locateFfmpeg` picks the ffmpeg: `IRVIS_FFMPEG` if set (capture-cli's `findFfmpeg` checks that it is an executable file), else, in a package (`app.isPackaged`), the bundled `resources/ffmpeg/ffmpeg` (`ffmpeg.exe` on Windows), else the first ffmpeg on PATH. Device listing and capture both use it. See [Bundled ffmpeg](#bundled-ffmpeg). Input is AVFoundation on macOS, V4L2 on Linux and DirectShow on Windows. Capture has no fixed duration limit. `IRVIS_TEST_CORS=1` enables the scheme's CORS privilege for the smoke experiment; production defaults to disabled. esbuild bundles the main process and CommonJS preload into `apps/desktop/dist`.

## Failure modes

Invalid IPC sources throw `Untrusted IPC sender`. A package without ffmpeg whose PATH has none either throws `This irvis package has no ffmpeg. Install ffmpeg and start irvis with IRVIS_FFMPEG set to its path.`; if the package's ffmpeg exists but cannot be run, the message is `The ffmpeg of this irvis package (<path>) is not an executable file. Reinstall irvis, or start it with IRVIS_FFMPEG set to another ffmpeg.`; from the repository the message is capture-cli's `ffmpeg not found: install it (brew install ffmpeg) or set IRVIS_FFMPEG to its path`, and a bad `IRVIS_FFMPEG` gives `IRVIS_FFMPEG=<path> is not an executable file` in both. Invalid mode/device throws `Invalid capture selection`. Invalid platform/device combinations throw `Invalid capture selection`. A different native format reports `Exact reference requires native yuyv422; received <format>`. Child errors and exit diagnostics are shown in the comparison status.

## Tests

`npm run test:desktop` builds both applications and runs Playwright's Electron smoke test. It checks bridge isolation, window preferences, module Worker, fetch, localStorage, a generated WebM video and CSP. ffmpeg must be installed to generate the temporary video. It also checks invalid capture selection and, on macOS, a fake ffmpeg process emitting a packed frame and a pixel-format log token split across writes, simulation metrics and the frame-pair download. The test holds back the format suffix to check that capture survives the partial token. Its fake ffmpeg continues emitting frames after the first fragmented frame, respecting stdout backpressure, because real capture may drop startup frames. It also verifies that reload terminates the old process and that a new capture can start and stop afterwards. A complete unsupported format still stops capture with an error. Hardware capture, simultaneous access and macOS privacy permissions require the owner procedure in [M3 findings](../findings/m3.md).

## Local recordings

`src/recordings.js` installs `recording:storage` handlers using the same main-frame sender authorization as capture. Files live in the `recordings` directory under Electron `userData`; renderer-supplied names must be alphanumeric/dot/underscore/hyphen and end in `.irvis`, `.pcm` or legacy `.webm`. Exclusive creation prevents overwrites. Writes handle short writes and reject concurrent requests; each append is limited to 4 MiB. Flush calls `FileHandle.sync`, and close syncs before releasing the file. The renderer recorder flushes every accepted thermal frame and audio packet, and stops accepting thermal frames if an append/flush takes more than one second. Listing includes unfinished files for scanner recovery. Remove rejects open sinks. Renderer termination closes idle handles and marks busy handles for sync/close when their current operation settles.

The desktop smoke test checks the packaged AudioWorklet under the app CSP, PCM sidecar listing/deletion, recording append/flush/close, byte-range reads, deletion and rejection of a traversal filename through the real preload IPC bridge, in addition to its existing capture and isolation checks.

Replacing the main-frame document (including reload) also stops capture and closes recording sinks. Storage cleanup increments a session generation, marks all old sinks before yielding and waits for in-flight opens/writes to sync and close. New IPC requests await this cleanup; requests that crossed the session boundary before opening a file reject with `Recording session closed.` Same-document navigation does not retire the session. Cleanup snapshots the old entries so later recordings cannot be closed by an earlier cleanup loop. The desktop smoke test leaves a valid recording unfinished and its handle open, reloads, recovers the thermal frame, deletes the file and reuses its name in the new session.

## Camera control

`control.js` opens the one USB device matching the selected profile; ambiguous USB matches disable control. The current driver supports `infiray-p2pro`. It serializes transactions using the existing `CameraUsb` protocol, reads state before capture and after commands, and polls `cur_vtemp` approximately every second without overlapping polls. Frames are dropped during transactions. Commands accept only profile command IDs; renderer bytes and arbitrary transfers are never accepted. On macOS the build compiles the existing IOKit helper into `dist/iokit-request`; other platforms use node-usb without claiming or detaching UVC. USB failures leave video available with assumed state, unless the mode requires an enable command; the main process then writes `Camera control is unavailable: <reason>` to stderr. Command attempts without control reject with `Camera control is unavailable`.

Snapshots contain `gain` (`high`/`low`, or `unknown` when the read fails or returns a value other than 0/1), raw TPD values under `usb-` keys, and hexadecimal `usb-pseudo_color` and `usb-cur_vtemp`. Failed reads omit other raw fields. Valid EMS and TU also populate `emissivity` (raw / 128) and `reflected-temperature` (raw − 273.15 °C); invalid or failed values become `unknown` so correction cannot silently assume unity. The renderer then keeps the camera's readings and recordings but does not apply Host correction (see [UI technical](ui-technical.md)). Unknown gain blocks temperature conversion. While `gain`, `emissivity` or `reflected-temperature` is `unknown` in a camera snapshot, the one-second poll repeats the full state read instead of reading only `cur_vtemp`, so a transient USB failure clears on the next successful read. Each full read that still leaves a value `unknown` doubles the wait before the next one (1, 2, 4, 8, 16 s, then every 30 s); the polls in between read only `cur_vtemp`, so a persistent failure or an out-of-range value does not keep the control `busy` and drop video frames every second. Any full read with all three known (poll, command or reconnect) resets the wait to 1 s. A failed periodic read removes stale sensor bytes. Closing capture cancels polling and closes USB after in-flight work settles. A generation check prevents an obsolete asynchronous open from launching ffmpeg.

`src/permissions.js` runs during build on macOS. It requires the Xcode command-line C compiler, builds the helper as a universal (arm64 and x86_64) binary and sets `NSCameraUsageDescription` in the development Electron.app Info.plist to `irvis uses the camera to display and record thermal images.` Packages set the same key themselves ([Packages](#packages)).

The `desktop` Vitest project tests per-platform input arguments, exact output, rejected selectors, USB ambiguity, command allow-listing, state reads, polling and cleanup with a fake USB device. Real camera capture and USB permissions on Linux/Windows remain hardware verification work.

The smoke test runs the packaged microphone AudioWorklet in an OfflineAudioContext for exactly 2048 frames and checks that its message contains nonzero oscillator samples. This verifies loading and execution under the app CSP without relying on a real-time audio output device. It does not verify microphone permissions or hardware audio timing. Frame-pair export waits for Electron's DownloadItem `done` event with state `completed` before parsing JSON; file existence alone does not establish download completion.

Command requests reserve a busy slot immediately, including time spent waiting for a sensor poll. A second request rejects with `Camera command is already in progress`; unknown IDs reject with `Unknown camera command` before USB traffic. Gain commands reread state and reject with `Camera did not confirm the requested gain` unless the returned gain matches. Before writing, the snapshot loses its old gain, so even a thrown readback cannot leave stale temperature conversion enabled. A failed command can still have changed hardware; a successful readback remains authoritative.

Each command attempt increments the snapshot's `command-generation` number. It is retained on subsequent reads. The existing .irvis state-change rule therefore starts a keyframe on the next recordable frame, including high → low → high; both supported gains now produce recordable frames, while unknown gain remains blocked. This is a host command boundary, not proof of sensor exposure synchronization: ffmpeg may buffer frames, and real transition timing remains in the [M5 checklist](../findings/m5-checklist.md).

Numeric profile commands accept `command(id, value)`. Main rejects a missing, nonfinite or out-of-range value with `Camera command value is outside the supported range`, and an argument on a parameterless command with `Camera command does not accept a value`, before any USB traffic. It copies the profile's first transfer and writes `round(value * scale + offset)` as a big-endian u32 at the declared byte offset. The renderer supplies no bytes, offsets or USB parameters. After the usual serialized sequence and full state read, mismatch at the declared raw snapshot field throws `Camera did not confirm the requested setting`.

See [M5 hardware observations](../findings/m5-hardware.md) for measured thermal effects, volatile settings, recording acceptance and the rejected NUC candidate.

## Packages

`apps/desktop/electron-builder.config.mjs` configures electron-builder 26. `npm run package:desktop -- <electron-builder options>` runs `npm run build` (web build, main and preload bundles, on macOS the IOKit helper) and then `electron-builder --config electron-builder.config.mjs --publish never` in `apps/desktop`. Without options it packages the host system and architecture. Packages go to `apps/desktop/release/` (ignored by git), named `irvis-<version>-<os>-<arch>.<ext>` with the version of `apps/desktop/package.json`, which the [Release workflow](../guides/development.md#release) sets; electron-builder writes `x86_64` (AppImage) and `amd64` (deb) for x64 on Linux.

| System | Options used in CI | Targets | Architectures |
| --- | --- | --- | --- |
| macOS 13 or later (Electron 45's `LSMinimumSystemVersion`) | `--mac --arm64 --x64` | dmg | arm64, x64 |
| Windows 10 or later (Electron 45's minimum; the installer does not check it) | `--win --x64` | NSIS installer (assisted, per user, installation directory can be changed) and zip | x64 |
| Linux | `--linux --x64` | AppImage and deb | x64 |

What a package holds:

- `app.asar`: `package.json`, `dist/main.cjs`, `dist/preload.cjs` and the production dependency node-usb (`usb`) with its runtime dependencies. esbuild bundles `@irvis/core` and the capture-cli modules into `main.cjs`, so `@irvis/core` is a development dependency. Of node-usb, only `LICENSE`, `package.json`, `dist/` and the one prebuild directory of the packaged system and architecture (`prebuilds/<platform>-*<arch>*`: the universal `darwin-x64+arm64`, `linux-x64` or `win32-x64`) are kept; electron-builder unpacks the `.node` file into `app.asar.unpacked`. `npmRebuild` is `false`: the prebuilds use N-API, which Electron loads as they are.
- In the resources directory (`process.resourcesPath`), outside `app.asar` so that they can be fetched and spawned: `web/` (a copy of `apps/web/dist`, including `THIRD-PARTY-LICENSES.md` with the licence texts of the npm packages bundled into the web build; fflate, the one third-party package that esbuild bundles into `main.cjs`, is among them, and nothing else carries its licence: a package that `main.cjs` bundles and the web build does not would ship without one), `ffmpeg/` (`ffmpeg` or `ffmpeg.exe`, `COPYING.LGPLv2.1`, `README.txt`), `libusb/` (`COPYING` and `AUTHORS` from `node_modules/usb/libusb/`), `LICENSE.irvis.txt` and `NOTICE.irvis.txt`; on macOS `iokit-request`; on Linux `60-irvis.rules`. The node-usb prebuilds link libusb (LGPL-2.1-or-later; 1.0.30 in node-usb 2.19.1) statically, which is why its licence ships here although the `libusb/` source directory of node-usb is left out of `app.asar`; the [Release workflow](../guides/development.md#release) attaches node-usb's source package, which holds libusb's source.
- Electron's own `LICENSE`, renamed `LICENSE.electron.txt`, and Chromium's `LICENSES.chromium.html`, which electron-builder keeps: in the resources directory on macOS, next to the executable on Windows and Linux. The package smoke test does not check them.
- The deb also installs `tools/capture-cli/60-irvis.rules` as `/usr/lib/udev/rules.d/60-irvis.rules` (through electron-builder's `deb.fpm`). It grants the logged-in user USB access to both profile PIDs, so camera commands work without root once the camera is plugged in again. The AppImage cannot install it; the [user document](desktop-user.md#install-a-package) gives the commands.

When `app.isPackaged`, `src/main.js` serves `resources/web` instead of `../../web/dist`, passes the bundled ffmpeg path to `locateFfmpeg` and runs `resources/iokit-request` instead of `dist/iokit-request`.

The config reads `electronVersion` from the installed `electron/package.json`: npm hoists Electron to the workspace root, and electron-builder refuses the `^45.3.2` range in `apps/desktop/package.json`. Its `beforePack` hook stops when `apps/desktop/ffmpeg/dist/<os>-<arch>/ffmpeg` (`ffmpeg.exe` for Windows) is missing, with `apps/desktop/ffmpeg/dist/<target>/<ffmpeg or ffmpeg.exe> is missing: run npm run ffmpeg:build -- <target>, or set IRVIS_PACKAGE_WITHOUT_FFMPEG=1 to package without ffmpeg`. With `IRVIS_PACKAGE_WITHOUT_FFMPEG=1` it prints `packaging <target> without ffmpeg; users must set IRVIS_FFMPEG` and packages without ffmpeg: the fallback for a system whose ffmpeg build fails.

Signing: none of the packages is signed for distribution. macOS packages carry an ad-hoc signature (`identity: '-'`) without the hardened runtime, because arm64 code must have a valid signature to run; Gatekeeper still treats them as from an unidentified developer. Their Info.plist sets `NSCameraUsageDescription` to `irvis uses the camera to display and record thermal images.` and `NSMicrophoneUsageDescription` to `irvis records optional microphone audio with a recording.` Signing and notarisation are separate work; the hardened runtime they need will also need the camera and audio-input entitlements. There is no application icon yet, so electron-builder uses Electron's. TODO(owner): an application icon.

## Bundled ffmpeg

`apps/desktop/ffmpeg/build.sh [mac-arm64|mac-x64|linux-x64|win-x64|source]` (`npm run ffmpeg:build -- <target>`; the default is the host) builds the ffmpeg that packages ship ([decision](../decisions/architecture.md#the-desktop-app-ships-its-own-lgpl-ffmpeg-build)). It downloads `https://ffmpeg.org/releases/ffmpeg-9.0.2.tar.xz` into `apps/desktop/ffmpeg/dist/`, stops unless its SHA-256 is `8c3850283eb25fa026482078a04051e0be17347b09ef81a0849bec15a96e002e` (the tarball whose FFmpeg release-key signature was checked when the version was pinned), and builds the unmodified source in `dist/build/<target>/`. `source` stops after the check; CI uses it to publish the tarball.

`configure` gets `--disable-everything --disable-autodetect --disable-doc --disable-debug --disable-network --disable-ffplay --disable-ffprobe --disable-swresample --disable-swscale --disable-x86asm`, then enables only the `pipe` protocol, the `rawvideo` demuxer, decoder, encoder and muxer, and the input of the system. Without `--enable-gpl`, `--enable-nonfree` or `--enable-version3`, the result is LGPL 2.1 or later. The rawvideo demuxer exists only so that `verify.mjs` can feed frames through a pipe.

| Target | Input | Threads | Linking | Built on |
| --- | --- | --- | --- | --- |
| `mac-arm64`, `mac-x64` | `avfoundation` | pthreads | system frameworks, macOS 13.0 minimum, the same as Electron 45 | macOS; `mac-x64` cross-compiles with `-arch x86_64` on an arm64 Mac |
| `linux-x64` | `v4l2` | pthreads | static | Linux with gcc and the static glibc |
| `win-x64` | `dshow` | Win32 | static | an MSYS2 UCRT64 shell, or Linux with mingw-w64 (`x86_64-w64-mingw32-gcc`) |

It writes `dist/<target>/` with `ffmpeg` (or `ffmpeg.exe`), `COPYING.LGPLv2.1` from the tarball and `README.txt`: the version, the licence, the source URL and SHA-256, and the `configure` arguments. On macOS the binaries are about 1.3 MB and on Linux 2.5 MB.

`node apps/desktop/ffmpeg/verify.mjs [target]` (`npm run ffmpeg:verify -- <target>`) runs the built ffmpeg and checks that `-version` starts with `ffmpeg version 9.0.2` without `--enable-gpl` or `--enable-nonfree`, that `-L` reports the GNU Lesser General Public License, that `-decoders` and `-encoders` list only `rawvideo` and `-devices` only the input of the system (`avfoundation`, `video4linux2,v4l2` or `dshow`), that `COPYING.LGPLv2.1` and a matching `README.txt` exist, and that three random 256×384 YUYV frames piped through `outputArgs()` from `src/capture.js` (the output arguments of every capture) come back byte for byte. It prints `ffmpeg verify (<target>): ffmpeg 9.0.2, LGPL, <input> input, rawvideo only, 3 YUYV frames passed through unchanged`; any failure prints `ffmpeg verify (<target>): <reason>` and exits with 1. `mac-x64` runs under Rosetta on an arm64 Mac.

## Package tests

`test/ffmpeg.test.js` (Vitest `desktop` project) covers `locateFfmpeg`: bundled before PATH, `IRVIS_FFMPEG` before the bundled ffmpeg, PATH when the package has none, and both messages when nothing is found.

`node test/package-smoke.mjs [unpacked app directory] [--ffmpeg-optional] [--launch <executable>]`, run in `apps/desktop` after packaging, checks the resources listed under [Packages](#packages), the bundled ffmpeg version, that exactly one node-usb prebuild directory of the system is packaged and, on macOS, both Info.plist strings and `LSMinimumSystemVersion` `13.0` (the minimum the [user document](desktop-user.md#install-a-package) states; an Electron upgrade that changes it fails here). It then starts the packaged executable through Playwright with a PATH from which every directory holding an ffmpeg is removed: the page shows `irvis`, `app.isPackaged` is true, and device listing succeeds (on macOS and Windows that runs the bundled ffmpeg). Capture start on a camera that does not exist (`99`, `/dev/video99` or `irvis smoke`) must end with `Capture ended (<code>)`, which proves on every system that the bundled ffmpeg was spawned; before that, camera control loads node-usb through its own dynamic import from `app.asar`, and every `Camera control is unavailable: <reason>` line the main process writes to stderr must give the reason `Camera control requires exactly one matching USB camera` (no line at all when a camera is connected and control opens). A second start with `IRVIS_FFMPEG` pointing to a missing file must make capture start fail with `IRVIS_FFMPEG=<path> is not an executable file`. With `--ffmpeg-optional`, a package without ffmpeg passes if capture start fails with the "no ffmpeg" message instead. On Linux it starts Electron with `--no-sandbox`, because an unpacked `chrome-sandbox` is not setuid root. `--launch` starts another executable of the same package with the same checks; CI uses it for the AppImage with `APPIMAGE_EXTRACT_AND_RUN=1`. It prints `package smoke: resources, bundled ffmpeg capture start, node-usb and IRVIS_FFMPEG precedence passed` (or, without ffmpeg, `package smoke: resources, node-usb, IRVIS_FFMPEG instructions and precedence passed`).

The [Desktop packages workflow](../guides/development.md#desktop-packages) runs `verify.mjs` and the package smoke test on every system. Neither proves capture from a real camera, camera permission prompts in a package, the udev rule on a real Linux desktop, or the AppImage started with FUSE and the Chromium sandbox on a Linux desktop; those remain owner checks on hardware.
