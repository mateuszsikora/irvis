# Viewer UI

## Data flow

`packages/ui/src/Viewer.tsx` receives a `CameraBackend`, `CameraProfile` and optional command dispatcher. It owns connection/configuration state and a first-frame flag; frames never enter React state. The session subscription retains the latest frame and a requestAnimationFrame loop invokes `FrameRenderer.draw` in `src/render.ts`. The drawing loop also detects settings changes and redraws the retained frame after Stop, without a new capture session. Cleanup unsubscribes, cancels drawing and closes capture; a generation counter closes late open results after stop or unmount.

`FrameRenderer` decodes YUYV or reconstructs planar frames using the selected mode's thermal rows, converts raw values using the declared gain, then uses core `autoRange` and `renderPalette`. Thermal replay frames carry their own conversion. Uncertain pixels do not affect automatic bounds. A private canvas supplies pixels to a transformed visible canvas; CSS controls enlargement and interpolation. The scale uses the same palette and applied bounds. Bounds and consistency messages update directly through DOM refs. All-uncertain scenes keep previous bounds and show `No certain temperature readings.`

## Interfaces

`ViewerProps.backend`, `.profile`, `.device` and `.modeId` are required. `device` is the backend's device id and `modeId` the profile video mode that Start opens; an empty value of either disables Start. The viewer does not enumerate devices or choose a mode: the app does. The optional `profilePicker` node is rendered before Start in place of the profile name (after `Synthetic scene · no camera needed` for the replay backend); without it the viewer shows the profile name, as in the parity harness. `captureError` optionally supplies the current adapter error to the same alert/status presentation as local errors. `command` is optional and used only if `capabilities.deviceControl` is true and a session is open. The app remounts the viewer on source, camera, profile and mode changes. Initial display: iron palette, automatic 20–40 °C fallback range, unlocked scale/orientation, 0° rotation, no mirroring or uncertain overlay, Clear rendering, Fit size, assumed high gain. Manual invalid edits never reach the renderer.

## Failure modes

Connection and drawing errors appear in an alert. Unsupported gain clears the image and replaces bounds with `Readings unavailable`; it never silently uses high gain. Plausibility checks compare certain scene extrema with profile measurement ranges, so they are advisory only. Camera control requires an explicit dispatcher: no fabricated USB commands are sent. Browser capture errors from the app adapter appear below the preview; Stop then Start retries capture.

## Tests

The Vitest project `ui` (`packages/ui/vitest.config.ts`) runs `test/**/*.test.{ts,tsx}` in jsdom with the setup file `test/setup.ts`, which raises Testing Library's `asyncUtilTimeout` from 1 to 5 seconds for every `findBy…` query and `waitFor`. On the former self-hosted CI runner the UI tests ran about four times slower than on a development machine (the second test of `test/photo-workflow.test.tsx`: 306 ms locally, 1215 ms in CI), and a wait of 1 second failed there; the 5 seconds stay for GitHub-hosted runners, which are also shared. The waits query by text (`findByText(…, { selector: 'button' })`), not by role: the first `ByRole` query on a mounted `Viewer` took 80 to 225 ms locally even when the element was already there, against about 1 ms by text ([testing guide](../guides/testing.md#react-component-tests)).

`test/viewer.test.tsx` covers ordered bounds, six palettes, declaration without commands, disabled hardware controls, orientation lock, late-open cleanup and the image-only view with and without camera commands. `test/render.test.ts` checks locked bounds across scenes, excluded uncertain extrema, overlay and transforms, and a frame of a mode without temperature data, YUYV and I420, drawn as colours, rotated, without readings or a photo and recording frame. Actual camera access and visual interpolation need manual verification with hardware.

## Image-only view

When the viewer's mode, the session's or else `findVideoMode(profile, modeId)` from `@irvis/core`, has `layout: null` and no photo or recording is open, it is an image-only view ([decision](../decisions/architecture.md#a-live-camera-shows-a-mode-without-temperature-data-as-its-image-only)). `FrameRenderer.draw` then turns a YUYV frame into colours with `yuyvToRgba`, and a browser's I420 or NV12 frame with `yuv420ToRgba`, and draws it rotated, mirrored and smoothed as set, sets the colour bounds to `No temperature data`, clears the warning and the readings, switches the alarm off and keeps no photo or recording frame, so `capturePhoto` throws `No rendered thermal frame is available.`. The preview header reads `IMAGE ONLY / <width> × <height>`, the empty view `This video mode has no temperature data: Start shows the camera’s image only.`, and the settings panel replaces measurements, palette, temperature range and the browser's camera state with a section `Image only`: `This video mode carries no temperature data, so measurements, palettes, temperature ranges, photos and recordings are unavailable. Choose a mode without “image only” in Video mode to see temperatures.` Uncertain pixels, the tracking shortcuts and the alarm status are not rendered; the colour bar and the readings get `hidden`, because the renderer holds their elements from its mount. The viewer expects its host to make `[hidden]` `display: none !important`, as `apps/web/src/viewer.css` does, so that a class's `display` cannot show them. Capture photo is disabled and recording gets `live` false. Camera commands stay for a mode the profile lists, such as the P2 Pro's `yuyv-256x192`, and are hidden for any other, which may belong to another camera.

## Workspace presentation

The viewer uses a preview column and a 300 px settings panel, stacking below 760 px. The canvas fits a bounded viewport with preserved aspect ratio at every rotation. Zoom changes both CSS dimensions and permits scrolling. Palettes use the core palette stops as CSS gradient previews; buttons expose `aria-pressed`. Binary display choices and orientation also use native buttons, and switches retain native checkbox semantics. Camera configuration remains in native selects with explicit accessible names. `apps/web/src/viewer.css` reserves space for select arrows, provides focus rings and reduced-motion support. The first-frame flag updates once per session; live pixels and range labels stay outside React state. `Icon.tsx` supplies decorative inline SVG controls; `src/index.ts` exports `Icon` so the app header can use the same set, for example `refresh` on its camera list button.

## Measurement analysis

`measurements.ts` stores objects in unrotated image percentages and converts them to bounded integer pixels with `geometry`. `analyze` uses core point/line/area/frame statistics; centre and point markers require `centreCounted`. Each marker's `label` is its formatted temperature (`formatTemperature` in the chosen unit), and a marker of a point, line or area carries the object's id in `object`; the names stay in the readouts text. Object IDs come from one counter in `Viewer`, shared by the `Add` buttons (`AnalysisControls`'s `newId` prop) and the pointer: it starts at 1 for each new source (`analysisRevision`) and never hands out an id below one already in use, so an id never repeats within a source. Clear/delete do not modify tracking. `AnalysisControls.tsx` owns draft correction and threshold inputs; only valid committed edits reach `ViewSettings.analysis`. All objects coexist without a count cap. Coordinates provide accessible movement and rectangle resizing without requiring pointer gestures; their inputs take any decimal (`step="any"`), since a dragged position is stored to 0.01 %.

The canvas takes pointer events while it shows temperatures (not in an image-only view, and only once `FrameRenderer.recordingFrame()` holds a frame). `pointer.ts` does the geometry: `imagePixel` undoes the `object-fit: contain` letterboxing and the rotation and mirrors of `FrameRenderer.present` to find the unrotated pixel under the pointer, or null outside the picture; `toPercent` stores that pixel as a percentage that `geometry` rounds back to the same pixel; `findHandle` returns the nearest point, line end or area corner within about 10 screen pixels (at least 1.5 image pixels), on a tie the selected object's, then the newer object's; `handlePixel` gives the pixel a handle sits on and `moveHandle` moves it. `Viewer` keeps one gesture in a ref, for one `pointerId`; other pointers are ignored until it ends with `pointerup`, `pointercancel` or `lostpointercapture`. A press of the same pointer while its gesture is still open means its release was lost, so the old gesture is dropped and the press starts a new one. A primary-button press on a handle selects its object and starts a drag that remembers the offset between handle and pointer; a mouse press elsewhere on the picture adds a `Point` there, selects it and starts a drag with no offset. A drag moves the handle only after the pointer has travelled `DRAG_PIXELS` (3) screen pixels, then puts it at the pointer's pixel plus the offset, clamped to the image. A touch or pen press off a handle is a tap: the point is added on `pointerup` at the lifting position, unless the pointer travelled `DRAG_PIXELS` first or the browser sent `pointercancel` because it scrolled. The canvas has `touch-action: manipulation`, so a touch scrolls and pinch-zooms but a double tap adds points instead of zooming the page; a non-passive native `touchstart` listener calls `preventDefault` when a single touch starts on a handle, so that touch drags the handle instead (React's touch listeners are passive). The pointer is captured for a drag. The canvas shows a crosshair cursor, `move` while a mouse is over a handle of an object that still exists (`overHandle` holds that object's id and is cleared when the pointer leaves the canvas).

`FrameRenderer` corrects thermal frames relative to their recorded camera state using `correctFrame`; untouched correction uses `settingsFromCamera`. Raw capture without camera metadata assumes no camera-side correction. Corrected values feed palette bounds, measurements, isotherms and the core alarm evaluator (high threshold, 0.5 K hysteresis). Region highlighting greyscales the surrounding pixels after isotherms; the optional uncertain overlay is painted last. Measurement shapes and certain markers' crosses are drawn on the source canvas before orientation transforms. Each marker is a 7-pixel cross, green (`#00ff80`) when its object is selected and white otherwise. Its temperature is written afterwards by `drawLabels` on the visible canvas, after `present`, with an identity transform, so the text stays upright and unmirrored; `orientedPixel` (in `pointer.ts`, the forward transform of `present` and the inverse of `imagePixel`) gives each marker's position there. The text is 8 px sans-serif, its width from `measureText`, stroked 2 px black under white fill so it reads on any palette colour. `placeLabel` puts a label 5 pixels right of its cross, else left, else 11 pixels below or above either side: the first spot inside the canvas that covers no cross and no label already drawn (each label counted with its 1-pixel outline); with no free spot, the first spot inside the canvas; with none inside, it is pushed against the canvas edge. A marker on the same pixel with the same text as an earlier one (the frame's maximum is also an area's) gets no second label. Captured photos and MP4 export read the visible canvas, so they carry the upright labels too. Readouts update through a DOM ref, without storing frame arrays in React. Alarm trigger changes update React state; an effect owns the oscillator and disconnects it on disable, Stop, error or unmount. Unsupported conversions clear readouts and turn off the alarm.

`Open thermal photo` reads PNG/snapshot bytes through `IrvisReader`, requires exactly one frame, closes live capture, clears objects and restores validated saved host correction metadata, falling back to the stored camera state. Generation checks ignore obsolete loads. No captured overlays become objects. The same loader handles gallery analysis and external files. The current palette is used; rotation and mirrors reset because captured thermal arrays already follow the image orientation. Correction drafts remount from restored values.

Tests in `test/viewer.test.tsx` cover object counts, deletion/reset, coordinate edits, adding and dragging objects on the image, unit changes, parameter validation, photo loading and audio cleanup. `test/measurements.test.ts` covers local extrema, uncertain markers and geometry; `test/pointer.test.ts` the pointer-to-pixel mapping and its inverse under all 16 rotations and mirrorings, the percentage round trip and handle picking; `test/render.test.ts` the temperature labels and their placement; `test/viewer.test.tsx` the grab offset, the drag threshold, a second pointer, other buttons, a lost release or pointer capture, the move cursor, and touch taps, swipes and cancels. Actual speaker output and camera accuracy require manual verification.


Alarm lifetime follows the source generation attached to each retained frame. The viewer rejects alarm results and late subscription emissions belonging to an obsolete generation, resets the React trigger on Stop/Start, and passes `ViewSettings.alarmGeneration` to the renderer. `FrameRenderer` resets core hysteresis when that generation changes. Display-only redraws of a retained frame after Stop remain possible but cannot trigger a live alarm in a new session before its first frame. Stopping photo analysis disables the alarm without discarding the photo or objects; re-enabling the switch resumes analysis of the retained photo.

Photo import errors use separate `photoError` state and the `Photo import failed:` alert prefix. They do not set the source failure status or mute its oscillator. `test/alarm-lifecycle.test.tsx` covers rejected imports, Stop/Start before new frames, obsolete frame emissions, and photo Stop/re-enable. `test/render.test.ts` verifies that hysteresis persists within a source but resets across source generations.


The viewer derives one current-source `failure` for both status and audio. Adapter `captureError` applies only when no photo is loaded; successful photo loading clears local errors, and subsequent photo rendering errors remain active. Returning to capture restores adapter error handling. `test/alarm-lifecycle.test.tsx` covers a pre-existing capture error, late capture errors during photo analysis, return to camera error handling and photo rendering failures.


## Photo capture and gallery

`ViewerProps.files` is the host's `HostFiles` (`src/files.ts`, exported by the package): `recordings`, an optional `RecordingStorage` from `@irvis/media`; `photos`, an optional `PhotoLibrary` from `src/photos.ts` (`list`, `save` and `remove` promise methods, operating on `SavedPhoto` records: `id`, `name`, `createdAt` and PNG `bytes`); and `saveAs(name, source)`, which saves a copy or an export where the user chooses and resolves without saving when the user cancels. The viewer and its components use nothing else for files and never choose how a file is stored or saved: `packages/ui` does not import `saveRecordingFile`. Without `photos`, Capture photo and Gallery are disabled with `Photo storage is unavailable in this host.`; external file analysis remains available. `PhotoGallery.tsx` lists newest first and owns/revokes thumbnail object URLs. Successful deletion removes the entry without mutating active analysis; failures retain it. `Download <name>` passes the original temperature-bearing bytes to `saveAs` under the photo's name; a failure shows as `Gallery error:`.

`FrameRenderer` retains a cloned thermal frame and capture metadata only after a successful draw. `orientPhoto` reorders raw values and uncertainty with the same mirrors-before-rotation transform used for the canvas. `capturePhoto` reads that canvas's RGBA pixels and calls core `exportRenderedPng` synchronously through its initial snapshot/copy phase, so subsequent frames cannot change the pending capture. Unsupported draws invalidate capture. Metadata records palette, applied range, unit, host correction and `capturedOverlays: true`; overlays themselves remain rendered pixels, never restored objects. Native pixel dimensions preserve the existing PNG requirement that IHDR and the embedded thermal frame agree. CSS zoom does not resample the photo. Recapturing an imported photo retains its recorded profile reference, frame rate and exact/reconstructed provenance through `captureMetadata`, rather than assigning the currently selected live camera.

Saving uses a UUID and timestamped filename. Capture errors use `saveError` with `Photo capture failed:` and do not affect camera alarms. The gallery is refreshed only after `PhotoLibrary.save` resolves. Opening a photo restores nested `correction` metadata (or the flat correction fields written by core `exportPng`) through `photoCorrection`, rejecting invalid corrections. Each successful open remounts draft controls and clears added objects.

`test/photo-workflow.test.tsx` exercises capture → gallery → fresh point/line/area analysis, a download through `saveAs` with the original bytes, deletion and storage failures. `test/host-files.test.tsx` checks that each of the five copies (Download .irvis, Download audio sidecar, Export MP4, a gallery Download and Export flattened PNG) goes through `saveAs` under its name, that a host without `recordings` or `photos` gets their controls disabled with their messages, that Stop saves no copy, and that there is no automatic MP4 export. `test/photos.test.ts` checks transformed raw values/uncertainty and metadata validation; `test/render.test.ts` reopens a captured rotated/mirrored frame. Browser rendering and actual device persistence still need manual validation.

## Recording controls

The viewer lays out three `.panel-card` sections below the preview toolbar. `Readings` (`aria-label`) holds the `Tracking shortcuts` group of `.chip` toggle buttons, the alarm status paragraph (`role="status"`, `.status-pill` with `is-armed` or `is-alert`) and the readings `output`; the section and the output both get `hidden` in an image-only view, because the renderer holds the output from its mount, while the shortcuts and the status are not rendered. While no tracking shortcut is on and `analysis.objects` is empty, the section also renders `Turn on a tracking shortcut or add a measurement to see readings.` as a `.panel-help` paragraph outside the output (not in an image-only view). `Photos` holds the `Gallery filter` group (All, Photos, Videos buttons with `aria-pressed`; choosing one also opens the gallery), a `Tools` group with Capture photo, `Open thermal photo` and Gallery, and the photo gallery itself, whose `Photo gallery` heading is an `h4` below the card's `h3`. `Open thermal photo` and `Open recording` are `.file-button` labels around a transparent file input that covers the label, so the input keeps its accessible name, focus and native picker. `RecordingControls` renders the `Recordings` card: a `.status-pill.is-recording` output `Recording · <seconds> s` while recording; Check recording storage (until it succeeds, with `Check recording storage once before the first recording.`), Record .irvis, Stop recording and Open recording in one row; the `Record microphone` switch and `Recording threshold` with the hint `0 = lossless` (`aria-describedby`, `aria-invalid` when not an integer 0–65535); a playback bar (Play recording, Pause recording, `Position` and `Playback speed` with visually hidden labels, Export opened recording); the `MP4 export` fieldset with `Recorded appearance` and `Smooth export` switches and an `Upscale` group of 1×, 2× and 4× buttons; and the recording list, hidden when the filter is Photos or the list is empty. Without playback, Export opened recording stands alone in an `.action-row`. `RecordingThumbnail` draws its preview on a canvas with the class `.recording-thumbnail`; the host sizes it. Errors use `.notice.error-notice`.

`RecordingControls.tsx` receives the host's `RecordingStorage` (`storage`) and `saveAs`, polls the renderer's retained unrotated thermal frame and submits distinct timestamps to the bounded recorder. The initial threshold comes from the profile's first conversion. Stop, capture failure and unmount stop recording; Stop finalizes the files and lists the storage again, and saves no copy. Finalized and unfinished files are listed on mount. Without `storage`, Check recording storage and Record .irvis are disabled and the card says `Recording storage is unavailable in this host.` **Download .irvis** and **Download audio sidecar** (the recording's `.audio-v2.pcm` or `.audio-v1.webm`) pass the stored file's source to `saveAs` under its name. `Viewer`'s MP4 export renders the MP4 in memory and passes it to `saveAs` as `<recording>.mp4`; nothing keeps it. Playback uses the host-injected `openRecording` and delivers thermal frames to the existing renderer, so all measurement and palette controls remain available. Starting capture or opening a photo closes playback.

`FrameRenderer.recordingFrame` retains a separate unrotated clone for recording. Recording view metadata includes palette, applied range, unit, correction and orientation. MP4 export renders to separate canvases, supports 1×/2×/4× scaling and optional smoothing, and never replaces the live canvas. Recorded appearance restores those metadata fields; measurement objects, tracking and isotherm settings are serialized and restored through validated metadata. The recording list supports selection, thumbnails and deletion; the gallery filter selects All, Photos or Videos. A preview failure reports an error and offers opening the recording; a dark preview alone is not an error. `Export opened recording` also handles externally picked files.

`PhotoAnnotations.tsx` draws text and pointer strokes over an original PNG preview with colour and size controls and undo/redo. Export creates a separate flattened PNG through canvas encoding, deliberately omitting temperature metadata, and passes it to `saveAs` as `<photo>-annotated-flat.png`. It never writes back to the photo library or changes the original bytes.

Playback correction is scoped to each opened recording. `Viewer` initializes it with validated `photoCorrection(reader.header.viewState)` (null means use the frame's camera correction), then subscribes to `recordedViewState` for accumulated correction changes during playback and seek. A correction change updates only the correction draft fields in the mounted `AnalysisControls`; its measurement ID counter and unrelated drafts remain intact. Identical metadata does not reset drafts on every frame. Opening another source still remounts the controls together with clearing its measurement objects. Applying or resetting host correction explicitly overrides recorded correction for the remainder of that open recording, including seeks. Reopening any recording restores file metadata and clears the override. Other analysis edits do not disable following recorded correction, and obsolete players cannot update it. `test/playback-correction.test.tsx` covers separate recordings, reopen, missing metadata, recorded changes, manual overrides, obsolete deliveries and independent measurement editing/deletion across correction changes.


Live recording timestamps are captured with `performance.now()` at the camera subscription boundary and carried through renderer snapshots as `receivedAt`. Redrawing settings does not change that timestamp. Recording ignores snapshots preceding the recording request and stores receipt times instead of the camera's independent clock so version 2 audio packets share the thermal timeline. Export/download/deletion recognizes `.audio-v2.pcm` sidecars and retains legacy `.audio-v1.webm` support; PCM export uses the declared shared clock and crops/pads to video duration.

## Live backend integration

Profile command buttons dispatch through the current session when no host command callback is provided. Rendering consumes Worker reconstruction when available and preserves desktop camera state in captured thermal frames. A camera-reported gain selects the conversion ahead of the host assumption; an unknown conversion disables readings. Raw USB state is not used as emissivity correction.

Missing gain in a camera-origin snapshot and explicit `unknown` gain disable readings, photos and recorded-frame output instead of falling back to the host assumption.

## Cross-runtime acceptance

`npm run test:parity` drives the actual `Viewer` with recorded fixtures through `createReplayBackend` in Chromium, WebKit and Electron. Min/max/centre text in C, F and K is compared with the Node result, alongside full precision measurement parity through `openRecording`. ## Camera command controls

`CameraControls.tsx` receives the selected profile, current snapshot, session frame source/mode, host-reset callback and optional command dispatcher from `Viewer.tsx`. Browser buttons stay disabled even when a dispatcher is supplied. A synchronous ref guard and disabled buttons prevent overlapping UI requests; status shows `Waiting for camera confirmation…`, then `Camera command confirmed.` or the dispatch error. Desktop gain dispatch resolves only after matching readback.

The P2 Pro panel distinguishes sensor gain from display range. Manual NUC (when absent from the profile), camera distance and camera-side temperature adjustment stay disabled with explanations. Low temperature range uses high sensor gain and High uses low gain. Both gains have reported conversions; unknown gain produces no readings or new recording frames. The renderer applies `ProfileConversion.minCelsius`/`maxCelsius` before host correction by merging exclusions into the uncertainty mask, which is retained in photos and recordings. A YUYV capture retains path `exact` even when some readings are outside range. Existing analysis, alarms and isotherms skip those pixels. Command generations force recording keyframes in either gain.

`CameraControls` displays `Sensor range control: Auto` or `Sensor range control: Manual` separately from the read-back gain, and subscribes to the current session only while Auto is enabled. Auto is disabled when the selected mode has no thermal layout, with `Auto requires a video mode with temperature data.` `sensor-range.ts` implements the inspected T7 host policy: initialize with a confirmed high-gain command, wait 100 frames, then require 100 consecutive raw-converted frame maxima above 160 °C to select low gain, or below 150 °C to return high. Host correction does not affect that decision. Commands share the panel's pending guard; every completion resets settling, failures exit Auto, and Manual stops automatic requests without changing the last confirmed gain. Unmounting the session ends the subscription. Auto preserves the user's transmittance; it does not copy Android's device-specific implicit transmittance changes. Both threshold directions and pending/error handling have software tests; the hot-kettle capture is not an above-160 °C physical test.

`test/camera-controls.test.tsx` covers browser denial, unsupported NUC, pending requests, completion and errors. Hardware acceptance is tracked in the [M5 checklist](../findings/m5-checklist.md).

The viewer advances `commandSession` on Start and Stop and includes it in the command panel's React key. Each connection therefore gets fresh status and pending state. Completion of a previous panel's asynchronous command cannot update the current panel. The viewer tests cover clearing a completed confirmation on Stop/Start and an old failure arriving while a new session's command is pending.

The viewer supplies the latest exact-frame camera snapshot to `CameraControls`, updating React state only when snapshot content changes. Numeric controls show current readback separately from the requested value and camera resolution; the request is rounded to the nearest encoded integer. Browser inputs and Apply buttons remain disabled. All fields and buttons are disabled while any command is pending.

`FrameRenderer.draw` uses `correctionFor` for host edits on live YUYV frames carrying camera state, matching the relative emissivity treatment already used for replay. With no host edit it preserves the camera's reading. Recorded/photo metadata carries the decoded camera correction, so later edits use the same baseline. When `cameraCorrection` rejects a live or replayed frame's state (for example `emissivity` or `reflected-temperature` is `unknown` after a failed USB read), the renderer skips Host correction for that frame, keeps the camera's own readings, measurements, photos and recording frames, and shows `CAMERA_CORRECTION_UNKNOWN`: "Camera correction could not be read. Readings are shown as the camera reported them; Host correction is not applied." Such a frame's view state stores the user's Host correction when one is set, otherwise `correction: null` (playback then uses the camera correction unchanged). The frame keeps its `unknown` camera state. `test/render.test.ts` covers live and replayed frames with and without Host correction. The atmospheric correction already applied in the camera is retained; the host still does not offer a separate atmosphere model.

`Reset camera correction` sends the allow-listed emissivity, ambient and reflected-temperature commands sequentially (1, 298 K, 298 K). Each command must confirm before the next is sent. Only full success clears host correction, so unedited readings follow camera correction with zero host offset. A failure leaves already confirmed writes applied and reports the error; no rollback or flash save is implied. Unmounting the session panel cancels remaining reset steps. `test/camera-controls.test.tsx` covers order, partial failure and session termination.
