# M1 findings: exact data via ffmpeg

The report of the M1 hardware spike ([#6](https://github.com/mateuszsikora/irvis/issues/6)) on the TOOLTOP T7 (InfiRay P2 Pro). Like every spike report, it says what was measured on one camera at one time; other documents do not cite it for what the code does ([decision](../decisions/docs.md#plans-and-spike-reports-live-in-docs-as-marked-exceptions)). The first part tells the owner how to run the spike; the remaining sections record the hardware sessions and outstanding reference checks.

Status: hardware streaming verified on 2026-11-15 after granting Terminal camera access; a packet-padding bug was fixed. The static-wall noise measurement is complete. The owner waived Android comparisons on 2026-11-15; absolute temperature accuracy remains unverified. Packed frames meet the expected image size, but original AVFoundation packets include 512 extra bytes, so the original packet-size acceptance criterion needs that documented qualification. Android agreement is no longer a completion requirement for this spike, by the owner's decision.

## Questions

From the [roadmap](../roadmap.md#m1-spike-exact-data-via-ffmpeg):

1. Does the camera send 256×384 YUYV with raw data right away, without any USB command?
2. What does the upper half look like: greyscale or a palette, and is its brightness monotonic in temperature?
3. Does every frame have 196 608 B?
4. Are the temperatures sensible (room about 20–25 °C, hand about 30–35 °C), and do they agree with the Android app within ±2 °C?
5. What are the latency and the frame rate stability?

## Run the spike

On the Mac, once:

1. Install ffmpeg: `brew install ffmpeg`. Until the app ships its own build (#23), the tool uses the first `ffmpeg` on `PATH`, or the one `IRVIS_FFMPEG` names.
2. Node.js 26 and `npm ci` in the repository ([development guide](../guides/development.md#setup)).
3. Plug the camera in directly, not through a hub if you can avoid it.

Then:

1. Run `npm run spike:m1` in the terminal app you normally use. The first time ffmpeg opens a camera, macOS asks whether the terminal may use it; allow it. If it does not ask and the captures fail with `no frames arrived`, allow the terminal in System Settings → Privacy & Security → Camera, restart the terminal and run the spike again.
2. Pick the thermal camera by its index. Every step and what to point the camera at is in the [capture tool](../features/capture-cli-user.md#run-the-m1-spike) document; the whole run takes about five minutes.
3. Paste the printed report (also in `captures/m1-<date>-<time>/report.md`) into #6. Keep the `captures/` directory: the fixtures issue (#16) takes short excerpts from it.

## Readings in the Android app

Optional procedure retained for future reference checks. The owner waived this comparison for #6 on 2026-11-15; no Android agreement is claimed.

The camera can be connected to one device at a time, so take the Android readings right before or after the Mac captures, at the same spots, from the same distance, without changing the scene. For each of `room`, `hand` and `mug`:

1. In the vendor's Android app, note the **centre** temperature (the crosshair in the middle of the image) at the spot the Mac capture points at.
2. Type it in when the spike asks, or add it later with `npm run capture -- reference captures/<session>/<scenario> <°C>` and run `npm run capture -- report captures/<session>` again.

Also note once, from the app's settings: the emissivity, the temperature range (high or low gain, "-20–150 °C" or similar), the distance setting, and the app and firmware versions if the app shows them. irvis assumes high gain and no emissivity correction; a different setting in the app explains a difference in readings.

## Hardware attempt: 2026-11-15

The connected camera was probed on a Mac14,9 (arm64), macOS 27.0.1 (26A434), using Homebrew ffmpeg 9.0.2 and Node.js 26.11.1. Local evidence is in `captures/m1-20261115/` (gitignored); this initial attempt captured no frames. No camera frames are committed.

- AVFoundation calls it `USB Camera` and advertises 256×192 and 256×384, both at 25 fps. Its index changed from 1 to 0 between discovery and capture. The first capture therefore selected a different camera and failed with `Selected video size (256x384) is not supported by the device.` This is not evidence that the thermal camera lacks that mode.
- The connected device identifies as `0x0bda:0x5840`, manufacturer `Generic`, product `USB Camera`, device version 19.0.3. The profile's USB filter at the start of the experiment was `0x0bda:0x5830`, so the ordinary probe missed it. A separate `probeUsb` call with the observed ID successfully read the configuration descriptor. After the owner identified it as TOOLTOP T7 and captures showed compatible image and thermal layouts, 0x5840 was added to the profile. Matching dimensions alone do not verify its temperature conversion.
- The USB descriptor declares YUY2, 16 bits per pixel, 256×192 with a 98304 B buffer and 256×384 with a 196608 B buffer, both at 25 fps. These are advertised sizes, not measured frame sizes.
- The UVC extension unit has ID 4, GUID `1229a78c-47b4-4094-b0ce-db07386fb938`, and two controls. Reading descriptors required no vendor commands.
- AVFoundation advertises `uyvy422`, `yuyv422`, `nv12`, `0rgb`, and `bgr0` for the larger mode.
- The corrected index-0 capture requested 10 s of 256×384 `yuyv422`. It received zero bytes and was stopped by the capture timeout; `initial-retry/meta.json` records the attempt and `ffmpeg.log` is empty.
- A separate 256×192 `yuyv422` test selected `USB Camera` by name, avoiding index changes. The debug log reached `'USB Camera' opened`, but no packet arrived within 15 s. A 256×384 `uyvy422` test selected by name reached the same point and also timed out without a packet.

A follow-up test launched from the standalone macOS Terminal produced a TCC `AUTHREQ_PROMPTING` event for `kTCCServiceCamera` attributed to `com.apple.Terminal`. The attempt timed out without frames; permission approval had not yet been confirmed at that point. The installed Conductor app has neither `NSCameraUsageDescription` in its Info.plist nor the camera entitlement in its signature, so Terminal was tried as the next diagnostic path. This does not by itself prove why the Conductor-launched process stalled.

At this stage camera access permission and the capture environment had not been ruled out. Failure in both modes did not establish that `y16_preview_start` was needed. The later Terminal authorization test below resolved the capture blocker.

## Successful capture after camera authorization

The owner accepted Terminal's camera permission and identified the device as a TOOLTOP T7 (no readable model marking on the housing). Captures run from the standalone Terminal then succeeded. Conductor's direct camera access was not retested; the later scenes were also captured through Terminal.

The first 3 s attempt produced only black frames. A 12 s capture started producing variable data after roughly 100 frames. Treat startup black/frozen frames as invalid temperature samples, not a confirmed NUC event. Short captures and whole-series averages that include startup are unsuitable for comparison with Android.

The original ffmpeg stream-copy output had **197120 bytes per packet**, although the image dimensions require 196608. The fixed-size splitter consequently shifted subsequent frames by 512 bytes each. The capture output now packs raw pixels without automatic pixel conversion, while `packets.framecrc` retains the original packet sizes. Older captures must be repeated.

### Verification of pixel preservation

Local evidence: `captures/m1-bytecheck-1794739019358/`. One 12 s camera session wrote both the original packets and the packed output:

- 300 source packets of 197120 B: 59136000 B total.
- 300 packed frames of 196608 B: 58982400 B total.
- Compared each packed frame with the first 196608 bytes of its corresponding source packet: **0 mismatched frames**, all bytes accounted for. The removed allocation tail was 512 B per packet.
- This verifies pixel preservation on this device/build. It does not turn the original packet sizes into 196608 B or prove that AVFoundation itself preserves the USB payload.

All use the corrected capture arguments, without vendor commands. Each original capture is retained. Therefore the excerpt's time-to-first-frame describes the original session startup, not the first retained sample. This was an experiment procedure, not a new CLI option.

The window is not a room-temperature reference. In the hand preview the hand is in the upper left, leaving the centre on the background; 18.7 °C must not be labelled a hand reading. Periodic frozen sequences and temperature steps remain visible after startup. They are detector candidates, not confirmed shutter events. No accepted NETD result follows from these non-uniform scenes.

### 90 s movement capture

Local evidence: `captures/m1-scenes-1794739393541/`. The owner was asked to move the camera slowly around the room and later reported that movement had stopped; the end is stationary. It is not a controlled 90 s motion sequence or a uniform-wall noise reference.

The full capture contains 2251 packed frames, no trailing bytes and a successful ffmpeg exit. Excluding the first 150 frames leaves 2101 frames over 83.93 s of arrivals: 25.02 fps by arrival, 25.00 fps by PTS, PTS interval SD 0.06 ms and no inferred missing frames. Arrival intervals have SD 5.6 ms, p99 50.2 ms and maximum 50.5 ms. The source packets remain 197120 B each.

The detector reports 18 NUC candidates (15 frozen sequences and 3 steps). Many frozen sequences last 12 frames, about 0.48 s. They are consistent with periodic interruption but are not confirmed shutter events. The report's 82 mK noise after subtracting the frame mean is only a diagnostic statistic from its chosen interval; it is not accepted as NETD for this scene. Conversion confidence and codec thresholds are unchanged.

### 60 s static-wall capture

The owner repositioned the camera from the window to a wall and was asked to leave it stationary. Local evidence: `captures/m1-scenes-1794739566312/`. The preview shows a wall with a smooth spatial temperature gradient rather than a perfectly uniform calibrated target. The original capture contains 1501 packed frames with no trailing bytes; the excerpt excludes the first 150 frames, retaining 1351.

- Preview frame 675 of the excerpt: centre **21.5 °C**, minimum 20.9 °C and maximum 24.1 °C. This is the room/wall measurement, replacing the earlier window as the room scene.
- PTS rate 25.00 fps, interval SD 0.06 ms and no inferred missing frames. Arrival rate 25.16 fps, interval SD 6.4 ms and maximum 54.4 ms.
- The longest interval without a detected event is excerpt frames 1094–1335: 242 frames from original PTS 49.754933 to 59.394933 s, a 9.64 s span within the 60 s static capture.
- Median per-pixel temporal noise **99.48 mK**, mean 104.25 mK; median after subtracting each frame's mean shift **58.98 mK**. The latter removes common-mode variation, not just random sensor noise. These are scene-based noise estimates using the reported 1/64 K conversion, not a calibrated laboratory NETD specification.
- The detector reports 13 NUC candidates (11 frozen sequences and 2 steps). Startup and early temperature shifts remain unsuitable for reference comparisons, even after the first 6 s; the whole-excerpt centre mean is not used as a calibrated wall reading.

The static-scene noise experiment is complete. Keep these measured estimates in the findings; camera-profile NETD and recording thresholds remain for #16, after reviewing event handling and calibration.

### Validation of the changes

`npm run lint`, `npm run format:check`, `npm run typecheck`, `npm run build` and `npm run docs-check` passed. `npm test` passed 36 test files: 343 tests passed and 1 was skipped. ### Decision

The profile now includes USB PID 0x5840 and retains reported conversion confidence. No `labelPattern` is added for the generic name `USB Camera`. Do not send `y16_preview_start` merely to address startup black frames: useful 384 data arrived without it. #20 should use the corrected packing arguments. #16 must exclude startup and investigate the frozen/step intervals before choosing noise or codec thresholds. The owner waived the Android comparison for #6; no change to conversion confidence follows from that waiver.
