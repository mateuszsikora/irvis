# M3: browser diagnostics and comparison

Status: real-camera capture and overlapping capture-cli comparisons completed in Chrome and Safari on macOS. Verdict: **works partly**. Native planar frames are available and average/centre statistics are close to the exact capture, but reconstructed minima differ and the 30 ms performance target is missed. The owner confirmed that the camera and scene remained stationary during these trials; pixel accuracy remains unmeasured. See the local measurements below.

## Owner procedure for #9

1. Use Node 26+, run `npm ci`, then `npm run spike:m3:web`. Open the printed localhost URL in Chrome on macOS. Repeat the procedure separately in Safari (and optionally Edge).
2. Point the camera at a static scene. Run `npm run capture -- list` to find its ffmpeg device index. In the page, refresh cameras, select the thermal camera and its 256×384 mode, then start and grant permission. Stop and reselect if permission was needed to reveal labels.
3. While the browser runs, execute `npm run capture -- capture --device 1 --seconds 10 --mode 384 --out captures/m3-chrome` with the correct device index and a new output directory for each browser. Keep scene, gain and camera settings unchanged. If concurrent capture fails, save the error; sequential captures are not equivalent evidence.
4. After ten seconds, stop browser diagnostics. Stop capture-cli too before checking that the camera indicator turns off (the concurrent CLI also keeps the camera active). Start and stop diagnostics again, especially in Safari, to confirm the device is released and reusable. Record any delayed release. Save **Download report** and **Download planar frame**. Rename files to include browser and scene. Run `npm run capture -- report captures/m3-chrome`. Keep its report alongside the browser files. If the browser rejects frames, save its report and status anyway.
5. Post the result record below and exported JSON files to issue #9. Keep large exact capture recordings locally. Record macOS version, browser version, camera name, gain and scene, and whether both captures actually overlapped.

## Negative capture check

In each tested browser, inspect `navigator.mediaDevices.getSupportedConstraints().resizeMode` in the developer console and record the value. When it is `true`, select a camera known not to offer the chosen profile dimensions natively (for example, a webcam without 256×384), then start diagnostics. Capture must fail with `OverconstrainedError` instead of producing reconstructed statistics. Save the report and the failed constraint name; the browser may report width, height or resizeMode. Do not assume a webcam lacks the mode without checking its native modes. If support is absent or the native modes are unknown, mark the check unverified. This check is separate from rejecting a VideoFrame whose coded dimensions differ: scaling to the requested dimensions would pass that dimension check.

The Chrome negative check was run on the FaceTime camera; see [constraint and lifecycle checks](#constraint-and-lifecycle-checks). Safari does not advertise resizeMode support, so this exact-constraint check is not applicable there.

The comparison averages each stream independently over an overlapping interval; samples are not paired. Exact-frame wall times are estimated from the capture metadata's completion time minus its monotonic duration plus each arrival offset. File-write/metadata overhead and processing delay limit that alignment. A 500 ms margin is removed at each end. The exact centre is the same single pixel as the browser (x=128, y=96), not capture-cli's centre-area statistic. All pixels, including uncertain ones, are included. Browser reconstruction timings come from sampled results, not a controlled benchmark on an idle machine.

**Verdict: works partly.** Both browser paths obtain physical-camera planar data and reconstruct a plausible scene average and centre while ffmpeg runs. Minima are materially lower than the exact stream's minima, and both miss the 30 ms target. The confidence mask does not establish accuracy: the saved Safari dump's minimum is marked confident. Limited-range metadata alone does not establish whether samples were remapped; no correction is inferred from that declaration. Bit-exact fraction, chroma-model agreement and p99 per-pixel error cannot be measured from these unpaired statistical windows. The owner confirmed that the camera and scene remained stationary. Thermal drift and the lack of frame pairing remain sources of uncertainty.

### Constraint and lifecycle checks

Chrome advertises resizeMode support. After opening the USB camera it returned `resizeMode: none` in track settings and `{ exact: 'none' }` in constraints. The FaceTime HD Camera was independently probed with ffmpeg: supported native dimensions were 1920×1080, 1280×720, 1080×1920, 1760×1328, 640×480, 1328×1760 and 1552×1552. It explicitly rejected 256×384. Chrome's exact request for that camera and size failed with `OverconstrainedError`, constraint `width`, and an empty browser message; no scaled-frame reconstruction was started.

Safari does not advertise resizeMode support and omits it from returned constraints. Its matching output dimensions therefore do not prove an enforced no-scaling restriction.

Chrome was stopped, the negative constraint check was run, and the USB camera was reopened successfully; a second Stop left the retained track in state `ended`. Safari's timed helper stopped its first capture and a subsequent real-camera capture succeeded. These checks demonstrate reopening on this machine, not a verified physical camera-indicator transition. ## Desktop comparison implementation (#10)

### macOS launch restriction encountered during the trial

Launching the capture through Conductor produced no frames. The macOS TCC log attributed both Electron and ffmpeg access to `com.conductor.app` and denied camera access because that responsible application lacked `com.apple.security.device.camera`; no permission dialog was allowed. Launching Terminal through automation retained that attribution. Starting the test manually from an independently opened Terminal allowed capture. This is a launcher restriction, not evidence that the camera is absent. No system privacy settings or application signatures were modified.
